# BT-V0-021 — Disconnected Publisher Session Recovery

Date: 2026-10-09. Follows BT-V0-020.

## Confirmed Production Failure

Production returned HTTP 410 from `POST /api/meetings/{meetingId}/media/publish`, with Cloudflare Realtime `errorCode: session_error` and `errorDescription: Session appears to be disconnected. Please check if the PeerConnection is connected.` BillionTalks had surfaced the upstream failure as HTTP 502.

## Root Cause

The Worker creates a Cloudflare publisher session on the first publish and stores `publisherSessionId` in the participant's Durable Object media state. Later publishes reuse that stored ID. When Cloudflare invalidated or disconnected the session, the ID and its publication mids remained stored until a separate recovery action, so subsequent publish requests could continue targeting the dead session.

## Changes

- **Immediate publisher-state invalidation:** a publisher mutation receiving Cloudflare 404/410 `session_error` clears the matching publisher session ID, published mids, pending publication state, and advances the publisher generation. Subscriber session and subscriptions remain intact.
- **Browser publisher replacement:** publisher recovery replaces the browser `RTCPeerConnection`; the old signaling/transceiver state cannot safely continue against a replacement Cloudflare session.
- **Enabled-track republish:** recovery reconciles only currently enabled media. Live microphone, camera, and active screen-share captures are reused; ended mic/camera tracks are reacquired. The browser's per-track publication map is cleared before publishing the enabled tracks once on the new peer.
- **Recovery and mutation coordination:** publisher publish reconciliation is blocked while recovery is pending. Recovery is deduplicated, serialized with publisher/subscriber mutations, and delayed responses from the replaced peer cannot mark stale tracks ready or mutate the current publication map.
- **Structured upstream diagnostics:** 404/410 remain distinguishable at the Worker API boundary and the response includes upstream status, Cloudflare error code, and error description. Successful publish responses include publisher generation.
- **Publisher diagnostics:** `btMediaDiagnostics()` includes publisher session generation, publisher connection/ICE/signaling states, publisher recovery count, last publish HTTP status, last Cloudflare error details, active local track names, and current publisher mids.
- **Subscriber isolation:** publisher invalidation and recovery do not clear or recreate the participant's subscriber transport.

## Validation

- `npm test`: 205 tests passed across six files.
- `npm run typecheck`: passed.
- `npm run build`: Wrangler dry-run passed; nothing deployed.
- Publisher regressions cover Cloudflare 410, state invalidation and replacement, retained subscriber state, browser peer replacement, single republish of enabled mic/camera/screen tracks, live capture reuse, recovery coalescing, and stale successful response protection.

## Physical-Device Checks Still Required

- Reproduce or observe the confirmed Cloudflare 410 on the affected device and verify the publisher state is invalidated.
- Verify the browser replaces its publisher PeerConnection and rejoins media using the new Cloudflare session.
- Confirm enabled microphone, camera, and any active screen share republish once without duplicate publications or lost media.
- Test ended-device-track reacquisition, concurrent failures, stale second tabs, and subscriber continuity on real browser/network timing.
- Inspect `btMediaDiagnostics()` from a device failure and confirm status, generation, error metadata, active track names, and mids are useful.
