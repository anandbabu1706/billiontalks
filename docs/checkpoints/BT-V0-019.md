# BT-V0-019 — Subscriber ICE Recovery Hardening

Date: 2026-10-08. Follows BT-V0-018 (`3956ee4`).

## Production-Test Defect

On a physical device the participant saw: `WebRTC ICE candidate gathering timed out.`, then the remote-playback warning (which stayed), then `Subscriber media transport recovered. Reconnecting active media.`. Local camera/mic worked; the remote tile stayed blank.

## Root Cause

The subscriber waited for ICE gathering to reach `complete` (10 s limit) before sending its answer. The offer had already been applied, so `ontrack` fired and a video element appeared, but the answer never reached `/media/renegotiate`. The server operation stayed pending and no media connection formed. The timeout was only a status message and triggered no recovery; the later recovery could hit the same stall.

## Changes

- **ICE-gathering timeout:** the subscriber answer wait uses `allowPartial`. The timeout is counted (`iceTimeoutCount`) and logged. The publisher wait is unchanged apart from diagnostics.
- **Partial-candidate continuation:** on timeout, if the local answer already contains `a=candidate:` lines, negotiation continues.
- **No-candidate recovery:** with no candidates the wait rejects with an `IceGatheringTimeout` error, which triggers subscriber recovery. Recovery also triggers on "no longer current" (stale operation) and on `Subscriber media connection ...` failures.
- **Connection wait:** after renegotiating new tracks, the subscriber must reach `connected` within 15 s, else it is recovered.
- **PeerConnection recreation:** recovery closes the old subscriber peer, clears remote streams/mid maps and elements, and `/media/recover` clears the server subscriber session. A new peer, fresh streams and fresh video elements follow, so `srcObject` is reassigned and the muted-autoplay fallback applies to the new element.
- **Active publication re-subscription:** the server's subscribed set is cleared, so the next `/media/subscribe` returns every active publication.
- **Stale `ontrack` protection:** `ontrack` from a peer that is no longer the active subscriber is ignored.
- **3-attempt recovery limit:** after 3 consecutive subscriber failures recovery stops and the status says remote media could not connect. The counter resets on a successful negotiation.
- **Unchanged:** publisher peer, local camera/mic, participant state, BT-V0-017 m-line ordering.

## `btMediaDiagnostics()` (`window.btMediaDiagnostics`)

`iceGatheringState`, `iceConnectionState`, `connectionState`, `remotePublicationCount`, `subscriptionResultCount`, `ontrackCount`, `droppedTrackCount`, `iceTimeoutCount`, `subscriberRecoveryCount`, `remoteVideoTrackReadyStates`, `mediaStreamTrackCount`, `videoSrcObjectAssigned`, `lastPlay` (`none`, `success`, or `failure:<name>`). Key events are also logged with `console.info('[billiontalks media]', ...)`. `window.btIceGatheringTimeoutMs` overrides the 10 s default (used by tests).

- `npm run typecheck`: passed.

- New tests (`tests/browser-ui.test.ts`): ICE timeout recovery with re-subscription and untouched publisher/local capture/join; partial-candidate continuation; fresh stream/element and stale track stopped; muted-autoplay fallback after recovery; no duplicate tracks/elements across three cycles and late stale `ontrack` ignored.
