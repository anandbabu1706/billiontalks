# BT-V0-031 - V0 Final Qualification Candidate

**V0 Final Qualification Candidate - physical release validation still required**

This checkpoint reconstructs the V0 final-audit fixes from BT-V0-FINAL-review.md on
baseline `21f47705f3352549e03abe351d4e410de0f31afa` (BT-V0-030). It is not the
formal BT-V0-FINAL sign-off. The release recommendation remains **NOT READY FOR
V0 SIGN-OFF** because the changed behavior has not completed production and
physical-device qualification.

## Reconstructed audit fixes

- Hardened meeting snapshots: prejoin, waiting, removed, and outsider callers
  receive only basic room data and their own participant/admission state; joined
  members receive the roster and only the host receives all admission requests.
- Retired unauthenticated `POST /api/realtime/session` with HTTP 410 before any
  upstream Cloudflare Realtime allocation.
- Reworked recording audio input handling around a stable recording-owned
  destination track. Local microphone, screen audio, remote participant audio,
  and remote screen audio are reconciled every 250 ms; muted inputs remain
  connected, while ended/replaced inputs are disconnected. Cleanup stops only
  recording-owned output tracks. Initialization and runtime mixer failures use
  an idempotent cleanup/reporting path that releases partial resources without
  stopping live meeting inputs.
- Unified publisher and subscriber automatic recovery into one bounded episode
  with six total attempts and a 30-second retry-admission budget. Startup or
  recovery terminal exhaustion suppresses later polling retries and requires
  leave/rejoin; the shared episode resets only after both media directions stay
  healthy for the stabilization period.
- Reset startup timing, failure counters, exhaustion state, and the shared
  recovery episode during same-tab transport teardown.
- Added an approximately eight-second timeout covering each server-side SFU
  request and response-body read, with abort handling and a sanitized HTTP 504.
- Cleared the meeting-duration interval whenever the meeting screen is left,
  while retaining server `createdAt`/`endedAt` semantics and keeping timer
  updates independent of media/network work.
- Hardened malformed percent-encoded cookies, invalid meeting identifiers before
  every meeting-specific session, storage, Durable Object, admission, media,
  recording, chat, and SFU route, and runtime JSON string/display-name inputs.
- Updated [README.md](../../README.md) to identify the current V0 audit scope
  and qualification boundary.

All BT-V0-030 media behavior, including camera publication identity and camera
OFF/ON restoration, remains in place.

## Required physical qualification before final sign-off

1. On host plus two guests, verify waiting and admitted visibility, approval and
   rejection, all access modes, removal, denied re-entry, unaffected guests,
   refresh, ordinary leave/rejoin without duplicates, and host end behavior.
2. On both host and guest devices, verify bidirectional audio/video, mute,
   camera OFF/ON, screen share/focus/stop, background/resume, and a short
   network interruption. Under prolonged interruption, verify the terminal
   recovery message, no automatic restart from polling, and successful
   leave/rejoin.
3. Start recording muted and before another participant joins. Unmute, add a
   guest, replace/recover a microphone, toggle cameras and screen share, stop,
   and inspect retained voices, videos, and synchronization through the
   existing authorized inspection process.
4. Refresh during recording, inspect persisted status, resolve the lost capture
   through stop/failure, start a new recording, verify duplicate start rejection
   across two tabs, and verify ordinary stop/finalization.
5. Exercise chat both ways; compare host/guest duration, refresh without
   resetting the start time, end/freeze the meeting, verify meeting history,
   and inspect desktop/mobile layout.

Known operational risks remain: abrupt browser closure can leave recording
metadata active until host resolution, recording requires supported browser
capture APIs and an active tab, and comprehensive server rate-limit/load
qualification is outside this audit.

No deployment, DNS change, Cloudflare secret change, binding change, merge to
`main`, or V1 work is part of this checkpoint.
