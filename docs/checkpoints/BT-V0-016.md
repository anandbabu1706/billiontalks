# BT-V0-016 — Live Media Hardening Consolidation

Date: 2026-09-28.

## Production-Test Issues Observed

- Remote camera/video could appear briefly and then disappear.
- Host microphone audio initially reached participants, while participant microphone audio was unreliable.
- Media transports could lose connectivity or become stale without a direction-specific recovery path.
- Screen sharing did not work on some mobile/browser combinations that do not expose `getDisplayMedia`.

## Pass 1–4 Fixes

- **Pass 1 — Publisher readiness:** The Worker stores successful SFU publisher allocations as pending. A joined publisher makes tracks discoverable only after the browser applies the SFU answer and the publisher PeerConnection reaches `connected`, then acknowledges the accepted track names. Pending allocations are included in cleanup.
- **Pass 2 — Remote track replacement:** Subscriber tracks are tracked by publication key and actual `MediaStreamTrack`. A replacement removes/stops the obsolete track, stale `ended` events cannot remove the replacement, duplicate stream tracks are avoided, and participant media elements are reused.
- **Pass 3A — Bidirectional microphone/autoplay:** Host and participant microphone publication share the same path. Mic OFF closes only the microphone publication; ON captures and publishes a fresh track. Remote playback rejection is surfaced separately with an explicit user-gesture retry and does not invalidate SFU state.
- **Pass 3B — Transport recovery:** Publisher and subscriber connection/ICE states are monitored. Brief disconnections receive a grace period; failed, closed, or stale transports recover through a serialized direction-specific operation. Only the affected SFU session and its publication/subscription locators are reset. Existing participant identity and meeting membership are preserved, then active media is reconciled.
- **Pass 4 — Screen-share capability:** `getDisplayMedia` is feature-detected. Unsupported browsers/devices see a disabled control and a concise explanation. Supported desktop sharing retains the existing SFU publication/readiness/recovery flow; stop closes only screen-share tracks, and restarting captures a fresh track.

## Validation

- `npm test`: 113 tests passed across five files.
- `npm run typecheck`: passed for application and tests.
- `npm run build`: passed with Wrangler dry-run; no deployment was performed.
- Focused regressions cover publication readiness, remote camera/microphone/screen track replacement, bidirectional mic publication and mic OFF/ON, autoplay rejection, direction-specific recovery, transient disconnects, stale subscriber sessions, screen-share capability, screen-share stop/restart, and media isolation.

## Remaining Live Validation and ADR Status

External-device testing remains required before production deployment: verify two-way microphone and camera across desktop browsers/devices; mic OFF/ON; transient network interruption and recovery for each direction; desktop screen-share start/stop/restart during active camera/mic; and the unsupported-screen-share message on a mobile/browser without `getDisplayMedia`.

This checkpoint does not claim external acceptance or change the ADR decision.

No production deployment, DNS change, Cloudflare resource change, or secret/configuration change is part of this checkpoint.
