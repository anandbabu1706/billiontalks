# BT-V0-030 - Startup Recovery Budget and Camera Republish Fix

Follows BT-V0-029. Real-device Test 56 passed bidirectional media, mute, the meeting timer and recording (4307851 bytes saved), but showed two failures.

## Failure 1: Guest Startup Still Took ~2 Minutes

Inference from code reading (not confirmed from production timings): publisher and subscriber recovery each had an independent cap of 3 attempts with their own backoffs, 10 s request timeouts and 8 s connection waits, running in series on a shared queue. Failure counters reset only after 30 s of healthy connection, so partial success did not stop the remaining recoveries. Individually bounded recoveries therefore summed to minutes. Normal startup does not enter recovery.

### Fix (src/index.ts)

- One shared startup budget, `MEDIA_TIMING.startupBudgetMs` = 30000, starting at the `joined` mark.
- Consulted by `requestMediaRecovery`, its retry scheduling, and the subscriber stale-session / no-remote-tracks retry paths.
- The budget ends when the publisher session is persisted and, if a remote publication was discovered, the first remote track has arrived.
- On exhaustion: no further hidden retries, one terminal console diagnostic, and the status `Media could not connect. Check your network connection and rejoin the meeting.`
- `btMediaDiagnostics().startupTransaction`: attempts, elapsedMs, completed, exhausted, terminalReason, publisherGeneration, publishStatus, publishReadyStatus, serverPublisherSessionPresent, discoveredPublications, subscriberGeneration, firstRemoteTrackAt.
- `window.btStartupBudgetMs` overrides the budget for tests.
- Trade-off: after exhaustion the user must rejoin.

## Failure 2: Camera OFF -> ON Froze Permanently

### Root Cause

Camera OFF stops the transceiver and closes the publication; ON publishes a new transceiver with a new mid. The server publication key was `userId:generation:trackName`, which is identical across OFF/ON. If the remote subscriber did not poll between OFF and ON, it saw an unchanged key, did not resubscribe, and stayed bound to the closed track (frozen last frame, audio unaffected). If it did poll during OFF, removal and re-add worked, hence the intermittent behaviour. The local sender, transceiver and stream were not stale.

### Fix

- Server publication key now includes the mid: `userId:generation:trackName:mid`. A republished camera is a new publication; the stale subscription is closed and the new one subscribed.
- After an explicit camera OFF -> ON, `verifyRestoredCamera` checks outbound video RTP; if flat it repairs the new sender with `replaceTrack`, then republishes once. Result recorded in `videoHealth`.
- Hard OFF retained so the remote receives an explicit removal; the old transceiver is not reused across OFF/ON.
- Audio, publisher peer and subscriber peer are not rebuilt.

## Tests

257 total (247 before, 10 added):

- Server: republished camera is resubscribed when the subscriber never polled between OFF and ON (fails without the mid in the key).
- Startup: normal startup has no recovery and exposes the full transaction; budget exhaustion stops retries with a single terminal diagnostic; recovery still works inside the budget.
- Camera, host and guest: OFF keeps audio untouched and ON restores a fresh live track without session rebuild; flat video RTP after ON is repaired via `replaceTrack`; remote element is not left on an ended track (weak in the harness; the server test is the real guard).
