# BT-V0-023 — Guest Publisher Readiness

Date: 2026-10-09. Follows BT-V0-022.

## Test 44 Production Evidence

The host's `/media/publications` diagnostics reported the host as `JOINED` with a publisher session and a camera publication, correctly excluded as `local-participant`. The admitted guest `Sr` was also `JOINED`, but had `publisherSessionPresent: false`, no published tracks, and was excluded as `publisher-session-missing`. Discovery consequently returned zero guest publications.

These observations establish the missing guest publisher state at discovery time. They do not by themselves establish which guest-side request or event caused it; Test 44 did not include guest `/media/publish` and `/media/publish/ready` request diagnostics.

## Guest Publish and Readiness

- The prior browser sequence waited for the publisher PeerConnection to reach `connected` after applying Cloudflare's publish answer and before calling `/media/publish/ready`. A slow or failed publisher connection could therefore leave server-side tracks pending rather than discoverable; recovery could then clear the publisher state before successful republish.
- The client now calls publish-ready after Cloudflare accepts tracks, the answer is applied, and the accepted tracks are confirmed. Readiness no longer depends on the browser PeerConnection reaching `connected`.
- `/media/publish` diagnostics report participant ID, a safe user-ID suffix, publisher-session presence and generation, and pending track names/mids. `/media/publish/ready` diagnostics report the same participant identity, session presence, promoted ready tracks/mids, and remaining pending tracks/mids.
- Browser `btMediaDiagnostics()` exposes participant ID and safe identity suffix, publish attempt count and HTTP statuses, publish-ready attempt/status, publisher generation and connection state, pending and ready track names/mids, and the last invalidation reason.
- Server lifecycle logs capture publish and ready starts/results, participant identity, safe identity suffix, generation, pending/ready tracks, and publisher-state invalidation with a categorical reason. They do not include Cloudflare publisher session IDs, bearer tokens, or raw credentials.
- Publisher invalidation logging covers recovery, stale upstream sessions, media connection replacement, transport closure, track-close invalidation, and participant media cleanup.

## Regression Coverage

- Verifies an admitted guest's publish request stores a publisher session and pending microphone/camera tracks, then publish-ready promotes both tracks.
- Verifies participant identity remains stable across admission, publish, and ready, and guest publisher state survives meeting refresh.
- Verifies publisher recovery can republish and make the guest's microphone and camera discoverable to the host under the same participant identity.
- Browser coverage verifies readiness proceeds after the Cloudflare publish answer is applied even if the publisher PeerConnection remains unconnected.
- Existing tests continue to cover host and guest publication/discovery behavior, including both host tracks.

## Remaining Validation

- Host microphone live timing remains unresolved; the server tests confirm it is discoverable after ready but do not establish physical-device timing.
- Physical-device testing is still required to capture the guest's publish and ready statuses, verify guest microphone and camera discovery on the host, confirm both media directions, and investigate delayed host audio with real devices.
