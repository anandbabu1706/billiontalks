# BT-V1-003 — Meeting Scheduler implementation

The approved scheduler layout is now connected to authenticated account-owned D1 scheduling. The dashboard keeps its approved card hierarchy and history statistics; its Next Meeting and Upcoming Meetings panels load persisted schedules.

## Persisted lifecycle

Migration `0005_scheduled_meetings.sql` adds the stable `btm_` meeting ID, account owner, title, agenda, local date/time, duration, original IANA time zone, resolved UTC start instant, guest-access policy, revision, and lifecycle status.

Lifecycle statuses are `SCHEDULED`, `STARTING`, `STARTED`, `ENDED`, and `CANCELLED`. `STARTING` is a retryable claim used while the host's Start action creates the existing V0 live room with the scheduled ID. Creating a schedule does not create a live room. Edits, cancellation, and start claims use revision checks. A guest following a not-yet-started link receives HTTP 425; a cancelled link receives HTTP 410.

Local times that do not exist during a daylight-saving clock advance are rejected. During a repeated local time when clocks move back, the earlier instant is selected deterministically. The local input and original IANA time zone remain stored alongside the UTC instant.

## API surface

- `POST /api/schedules` — create a schedule.
- `GET /api/schedules` and `GET /api/schedules?upcoming=1` — list owned schedules.
- `GET /api/schedules/{meetingId}` — view one owned schedule.
- `PUT /api/schedules/{meetingId}` — revision-checked edit.
- `DELETE /api/schedules/{meetingId}` — revision-checked cancel.
- `POST /api/schedules/{meetingId}/start` — authenticated host start of the existing live-room workflow.

External calendars, recurring meetings, contacts, invitations, RSVP, and paid integrations remain out of scope. The migration and code are not applied to Cloudflare by this implementation.
