# BT-V0-027 — Media Recovery Latency and Playback Hardening

Follows BT-V0-026. Core media (two-way audio/video, screen share, background/resume recovery) worked in production, but three UX problems remained, and Test 52 added intermittent subscriber failures.

## Production Observations

- Background/resume recovery took roughly 15–30 seconds.
- `Enable playback` repeatedly reappeared even after the user had interacted with the meeting.
- Transient low-level text such as `A media connection, offer, and valid local tracks are required.` was visible during recovery.
- Test 52: the host saw `Cloudflare Realtime did not accept any remote tracks.` and the mobile guest saw the terminal `subscriber media could not connect...` message. Fresh two-way media could still work, but subscriber negotiation was intermittent and slow.

## Timing Bottlenecks Identified

- ICE gathering waited up to 10 s even when candidates already existed.
- The subscriber connected-state wait was 15 s and blocked the subscriber queue.
- Media fetches had no timeout.
- Recovery awaited the operation queue, so it sat behind stuck waits.
- Subscriber recovery was serialized behind the whole publisher republish, and was reached only after the 2 s disconnect debounce.
- Resume recovered only the publisher; there was no subscriber health check.
- Remote peers rediscovered a republished publication only on the 3 s poll.
- 410 classification depended on message text.
- `no remote tracks accepted` had no rediscovery or retry path.

## Changes

Timing and bounds (client script in `src/index.ts`, `MEDIA_TIMING`):

- ICE gathering: hard timeout 10 s → 5 s, with early exit once a candidate is present plus a 1 s grace.
- Subscriber/peer connected wait: 15 s → 8 s.
- Media request timeout: new 10 s, with abort of superseded in-flight requests when recovery starts.
- Recovery queue drain bounded to 1.5 s instead of an unbounded await.
- Meeting poll: 1 s for 20 s after resume/recovery, otherwise 3 s.
- Recovery retry backoff 0.5 s / 1.5 s within the existing 3-attempt bound; unmute grace 0.8 s before reacquiring a live-but-muted track.

Recovery behaviour:

- `visibilitychange`, `pageshow`, `focus`, and `online` run an immediate subscriber/publisher health check. The subscriber is rebuilt if failed, closed, or disconnected, or after 15 s hidden; otherwise publications are re-discovered at once.
- A successful publisher-ready triggers publication rediscovery immediately instead of waiting for the poll.
- 404/410 are handled via structured upstream status, triggering immediate bounded session reconstruction. Dead subscriber sessions are never retried against.
- `no remote tracks accepted` triggers bounded retries (0.4 s, 1.2 s) that re-discover current publications and track locators first, then a single subscriber rebuild after retry exhaustion. Only then is the terminal subscriber failure shown.
- Fix: the retry counter was previously reset after the rebuild, which could produce an unbounded rebuild loop. It now resets only on success or leaving the meeting.
- Generation/stale-response protections and the 3-attempt recovery bound are preserved.

Playback / autoplay:

- Cause: any `play()` rejection, including `AbortError` (fired when `srcObject` was reassigned to the same stream on every render or tracks changed during renegotiation), was treated as "user interaction required", and nothing remembered prior interaction or cleared the warning.
- Existing remote media elements are preserved; `srcObject` is assigned only when it changes.
- `AbortError` is retried quietly; only a real rejection (e.g. `NotAllowedError`) shows `Enable playback`.
- A user gesture is remembered, triggers a best-effort unmuted play, and the unlocked state is reused for new streams. The warning clears automatically when playback succeeds. Browser autoplay policy is not circumvented; the muted-video fallback remains.

Status UX:

- Expected automatic recovery shows `Reconnecting media…` then `Media connected`. Low-level text (including the prerequisite error) goes to the console. The terminal rejoin message appears only after bounded recovery fails.

Diagnostics:

- `btMediaDiagnostics().mediaTimings` and console logs record resume detected → recovery started → publisher ready → publication discovered → subscriber negotiated → first remote track → first media playback.

## Tests

Final suite: 229 tests passing (9 added in the BT-V0-027 block), with typecheck, build (`wrangler deploy --dry-run`), and `git diff --check` clean. New coverage: immediate 410 recovery, resume health check, publication refresh after publisher-ready, `AbortError` vs real rejection, warning clearing, unlocked playback surviving subscriber replacement, no low-level error exposure with bounded recovery, and the `no remote tracks accepted` retry (success path and bounded exhaustion).

## Remaining Validation

- Real-device latency on iOS/Android after background/resume; timings should be read from `mediaTimings`.
- Browser autoplay policy and gesture rules (especially iOS Safari).
- Remote rediscovery still relies on polling (1 s/3 s); there is no server push.
- Cloudflare per-track error behaviour needs Test 52-style re-validation.
