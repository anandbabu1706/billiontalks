# BT-V0-018 — Production Meeting Media Stabilization

Date: 2026-10-07. Follows BT-V0-017 (`e1b8fe0`).

## Production-Test Defects

- Mic/camera shown ON on entering a meeting but nothing captured or published ("Media not connected").
- Admitted participant's camera not visible to the host.
- Screen share rendered locally but not remotely.
- "Copy meeting link" did not copy.
- Developer Tools visible in production.

## Fixes

- **Initial mic/camera auto-publication:** local state defaulted to ON with no stream, and joining only published existing tracks. `showScreen('meeting')` now captures and publishes any device shown ON, using the manual-toggle code path. This covers direct join, host creation and waiting-room approval (which previously never published). Prejoin buttons now behave like the in-meeting controls, and stopping a device cancels a capture still in flight.
- **Remote participant media stabilization:** the local tile is identified by user id rather than display name, so a participant sharing the local name is no longer treated as local.
- **Shared publisher/subscriber queue:** both directions mutate one per-participant server record, so concurrent requests could overwrite each other or return "Finish the pending media negotiation". All media signaling now runs on one chain, and a publish retries (max 3) after that error.
- **Autoplay muted fallback and enable-audio:** unmuted remote video is blocked by autoplay policy when the stream carries audio. Video now falls back to muted playback, the enable-audio button is shown, and pressing it unmutes. Audio-only elements keep the previous blocked behavior.
- **Remote media diagnostics:** each remote tile exposes `data-media-state` (`no-publication`, `no-subscription`, `no-track`, `not-assigned`, `playback-blocked`, `playing`). The subscribe response includes `diagnostics` (discovered publications per publisher, subscribed count).
- **Screen-share playback stabilization:** the separate `screenStream` element gets the same muted fallback and diagnostics. BT-V0-017 transceiver ordering and the non-forced close flow are unchanged; forced close remains teardown/recovery only.
- **Copy-link fallback:** Clipboard API first, then select-and-copy; the button shows "Link copied" or "Copy failed", and on failure the link is shown for manual copy.
- **Developer Tools gating:** the panel markup and enabling flag are only rendered on localhost/127.0.0.1/[::1] or when `DEV_TOOLS_ENABLED` is `"true"`. Simulated rooms skip all real media, and developer actions refuse to replace a real meeting.

## Validation

- `npm test`: 188 tests passed across six files (172 before).
- `npm run typecheck`: passed.
- `npm run build`: Wrangler dry-run passed; nothing deployed.
- New coverage: join and waiting-room auto-publication, each diagnostic state, autoplay fallback and unmute, remote screen as a distinct element, copy success/fallback/failure, Developer Tools gating and isolation. Existing tests that relied on toggling twice to start capture were updated.

## Physical-Device Checks Still Required

- Mic/camera capture at join and after waiting-room approval with real permission prompts.
- Muted-video autoplay fallback on iOS Safari and Android Chrome.
- Remote camera and screen share visibility between two real devices.
- Copy link in the production browsers in use.
- Shared signaling queue under real network timing (a slow publish can delay subscription up to 15 s).
- Cloudflare's real responses to the non-forced `tracks/close` calls from BT-V0-017 (still unconfirmed).
- Camera tile is hidden while a remote screen share is shown; confirm that is acceptable.
