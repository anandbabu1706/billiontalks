# BT-V0-029 - Guest Initial Publisher Startup and Meeting Duration Timer

Follows BT-V0-028. Real-device validation showed a startup asymmetry: the participant saw the host almost immediately, while the host waited 30+ seconds for the participant.

## Production Symptom

During the delay the host's `/media/publications` listed the guest as `state: JOINED`, `publisherSessionPresent: false`, `publishedTracks: []`, `exclusionReason: publisher-session-missing`. The delay was therefore before host subscription: the guest's publisher session was not created promptly.

## Root Cause

The `/media/publish` handler returned HTTP 409 "Finish the pending media negotiation before publishing." whenever the user's SFU state had `pendingSubscriptions`.

A guest joining after the host immediately subscribes to the host's tracks, so `pendingSubscriptions` is open exactly when the guest's first publish arrives. The publish got 409. The client fallback was `refreshSfuSubscriptions().then(publish)` (max 3 tries), and that refresh queues behind the in-flight subscriber negotiation (8 s connected wait, ICE waits). The publisher Cloudflare session is only created by a successful publish, so `publisherSessionPresent` stayed false until the subscriber side settled.

## Why the Host Was Unaffected

The host joins first with nothing to subscribe to, so it never has `pendingSubscriptions` at its first publish.

## Changes (src/index.ts)

- **Removed the server-side publish guard.** Publisher and subscriber use separate Cloudflare sessions, and the per-user SFU mutation lock already serializes handlers. The publish handler saves via `{...state}`, so `pendingSubscriptions` and `subscribedTracks` are preserved.
- **Legacy 409 fallback retained** on the client (bounded: `publishRetryCount < 3`), for an older server. "pending media negotiation" is now masked as `Reconnecting media…` and logged to the console.
- **Initial 410 / session_error** still uses the existing bounded publisher recovery.
- Publisher queue remains separate from the subscriber queue; mic and camera go out in a single publish.

## Startup Timing Diagnostics

`btMediaDiagnostics().startupTimings` (also logged as `[billiontalks media startup]` with offset from join):

`joined`, `captureRequested`, `captureReady`, `publishStarted`, `publishHttpResponse`, `answerApplied`, `publishReadyStarted`, `publishReadyCompleted`, `publisherSessionPersisted`, `firstRemotePublicationDiscovered`.

Expected sequence: joined -> capture requested -> capture ready -> publish started -> publish HTTP response -> answer applied -> publish-ready started -> publish-ready completed -> publisher session persisted -> (host side) first remote publication discovered. The host's discovery time is recorded by the host client when `/media/publications` first returns a publication.

## Meeting Duration Timer

- Shown in the meeting header (`#meetingDurationTimer`) as `HH:MM:SS`.
- Computed from the server-set meeting `createdAt`, not local join time, so host and participants show the same value and a refresh, reconnect or rejoin does not reset it.
- Clock-skew correction: each meeting refresh reads the HTTP `Date` header and keeps an offset from the local clock.
- When the meeting is no longer active, the value is `endedAt - createdAt` and the interval is cleared (frozen).
- One 1 s `setInterval` updating a text node: no network calls, no WebRTC/media impact.
