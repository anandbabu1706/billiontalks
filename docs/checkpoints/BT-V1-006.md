# BT-V1-006 — Recording Modes & Transcript Foundation

## Recording behavior

- The host may record audio, video, or both; both remain selected by default. Video uses the existing composed meeting-stage capture and audio uses the existing mixed meeting audio.
- Starting with other joined participants first requests their consent. Recording begins only after all joined participants accept and the host starts it. A participant decline leaves the request `FAILED`; the host may cancel a pending request.
- Participants joining an active recording are prompted separately. Their video and audio are excluded until they consent; a decline does not stop other participants' recording.
- Recording metadata is persisted in the existing meeting Durable Object. R2 object keys and multipart upload IDs are never returned to clients.
- The host capture sends a heartbeat every 20 seconds. Metadata without a heartbeat for two minutes is marked `FAILED/INTERRUPTED`; it is not presented as a completed recording. The authorized meeting recording-status read attempts to abort its incomplete private multipart upload.
- `GET /api/recordings` requires an authenticated account and lists only recordings associated with that account's meeting history. Existing per-meeting metadata reads continue to require meeting participation. R2 remains private; no direct recording download or playback access is introduced.

## Transcript foundation

Transcript envelopes and typed transcript records associate `meetingId` and `recordingId`, support optional speaker IDs and start/end timestamps, and carry explicit processing states. Authorized transcript reads return `UNAVAILABLE` with an empty record list. No transcript text is generated, and no transcription provider or background processor is configured.

The implementation adds no D1 migration: recording, consent, and transcript foundation data use the existing meeting Durable Object. Existing recordings without transcript state are reported as unavailable.
